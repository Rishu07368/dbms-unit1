1. Database Concepts 🔴 MUST KNOW 2M ××× · 5M intro

Intuition: A college keeps student details in files, marks in registers, fees in spreadsheets. A database puts all related facts in one organized place so many people and programs can store, search and update them safely. The DBMS is the software that manages that place.

📌 Definitions (write these word-for-word) Data: A collection of facts that can be recorded and which have implicit meaning.
Database: A collection of interrelated data, stored together to serve multiple applications; it can be of any size and complexity, generated manually or computerized.
DBMS: A collection of programs that enables users to create and maintain a database — general-purpose software for defining, constructing and manipulating the database for various applications.
Database System: A computerized system whose overall purpose is to maintain information and make it available on demand.

Core explanation

  • A database permits not only retrieval of data but also continuous modification needed for control of operations.
  • Example fields of a Customer table: cname, cno, ccity.
  • Applications (PDF list): Banking (all transactions), Airlines (reservations, schedules), Universities (registration, grades), Sales (customers, products, purchases), Online retailers (order tracking, recommendations), Manufacturing (production, inventory, supply chain), Human resources (employee records, salaries, tax deductions).
💡 ExampleCustomer database row: Ravi | C101 | Delhi — the values are data; the whole organized collection of such rows is the database; MySQL/Oracle managing it is the DBMS.
✍️ 2-mark exam answer — "Define DBMS""A DBMS is a collection of programs that enables users to create and maintain a database. It is general-purpose software that provides processes of defining, constructing and manipulating the database for various applications. Examples: MySQL, Oracle."
🎯 Examiner focusKeywords that earn marks: "collection of interrelated data" (database), "defining, constructing, manipulating" (DBMS). Don't write "DBMS is a database" — the DBMS is the software, the database is the data.

Likely 2-mark questions

Define Data with an example.
Data is a collection of facts that can be recorded and which have implicit meaning. Example: a customer record with cname = Ravi, cno = C101, ccity = Delhi.
What is a database? Give two applications.
A database is a collection of interrelated data stored together to serve multiple applications. Applications: (1) Banking — transactions; (2) Universities — registration and grades.
Differentiate: Data vs Database.
Data = raw recorded facts (e.g., "Ravi, C101, Delhi"). Database = an organized collection of interrelated data stored to serve multiple applications.
What is a Database System?
A computerized system whose overall purpose is to maintain information and make that information available on demand.

🧠 Active recall

State the three verbs describing what a DBMS does to a database.
Defining, constructing, manipulating.
Name any four DBMS applications from the PDF list.
Banking, airlines, universities, sales (also: online retailers, manufacturing, HR).
Is a hand-maintained register a database?
Yes — the PDF says a database may be generated and manipulated manually or computerized.

📌 DefinitionsActors on the scene: people whose jobs involve day-to-day use of the database. Workers behind the scene: people who build and maintain the DBMS environment itself, without using the data.

3. DBMS Architecture 🔴 MUST KNOW 2M ×× · 5M + diagram

Intuition: A library has three views of the same books: the visitor's catalogue (what you see), the librarian's master register (how it's logically organized), and the actual shelves in the basement (how it's physically stored). DBMS architecture separates these so each can change without disturbing the others.

B. Three-level ANSI-SPARC architecture ⭐ (the big 5-marker)

📌 DefinitionThe ANSI-SPARC architecture describes a database at three levels of abstraction — External (view), Conceptual (logical) and Internal (physical) — whose objective is to separate each user's view of the database from the way the database is physically represented. Most commercial DBMSs are based on it.
Fig 3.2 — ANSI-SPARC three-level architecture with the two mappings.
🖊 How to draw in the exam: Step 1 → draw 3 small boxes on top (external views) with users above. Step 2 → one wide box in the middle (conceptual). Step 3 → one box below (internal) + a cylinder/ellipse (storage). Step 4 → arrows between levels labelled "External/Conceptual mapping" and "Conceptual/Internal mapping". Step 5 → tag the levels: view/logical/physical.
LevelAlso calledDescribesDeals with
External (highest)View levelOnly the part of the database an end user cares about; many views can exist for the same DBEnd-user views

💡 Advantages (write 4–5 in exam)① Provides data abstraction (hides low-level complexity). ② Same data accessible by different users with different customized views. ③ User need not know physical storage details. ④ Physical storage can change without affecting users' views. ⑤ Conceptual structure can change without affecting end users.
✍️ 5-mark structure — "Explain three-level architecture with diagram"1) Definition + purpose (data abstraction) — 1 mark · 2) Labelled diagram — 1.5 marks · 3) One point per level (what/who) — 1.5 marks · 4) Two mappings + one advantage — 1 mark.
🎯 Examiner focusMust write: "WHAT data" = conceptual, "HOW stored" = internal. Mention both mappings by name. The diagram is compulsory for full marks. Common twist: "Which level describes compression/encryption?" → Internal level.
⚠️ Common mistakes✗ Swapping conceptual and internal descriptions. ✗ Saying "one view per database" — there can be many external views. ✗ Forgetting that 3-tier (machine) architecture ≠ 3-level (ANSI-SPARC) architecture — different concepts, both in the PDF.

Likely 2-mark questions

What is the external level?
The highest level of data abstraction; it describes only that part of the database a particular end user is concerned with. Many different views can exist for the same database.
What is the objective of the three-level architecture?
To separate each user's view of the database from the way the database is physically represented, so users get customized views and the DBA can change storage or conceptual structure without affecting users.
Differentiate 2-tier and 3-tier DBMS architecture.
In 2-tier, the client application communicates directly with the database server (via ODBC/JDBC). In 3-tier, an application server sits between them — the client talks to the application server, which internally talks to the database.
Which level deals with data compression and encryption?
The internal (physical) level — the lowest level of abstraction, describing how data is actually stored.

🧠 Active recall

Order the three levels from highest to lowest abstraction.
External → Conceptual → Internal.
Which mapping gives logical data independence?
External/Conceptual mapping.
Who works mainly at the conceptual level?
DBA, database designers, application developers.

5. Data Independence 🔴 MUST KNOW 2M ×× · 5M

Intuition: You can renovate the godown (physical storage) without telling shop customers, and you can rearrange the catalogue (logical structure) without changing what customers see on their phones. That "change one layer without breaking the others" is data independence.

📌 DefinitionsData independence: the ability to change the database structure at one level without affecting application programs, users, or the other levels.
Physical data independence: changes in physical storage do not affect the logical structure.
Logical data independence: changes in the logical structure do not affect user views / application programs.

Likely 2-mark questions

What is data independence?
The ability to change the database structure at one level without affecting application programs, users, or other levels. Two types: physical and logical data independence.
Differentiate physical and logical data independence.
Physical: storage changes (file organization, devices, indexes) don't affect the logical structure. Logical: logical changes (new columns, table changes, splitting relations) don't affect user views or application programs.
Give two examples of changes requiring physical data independence.
(1) Changing the file organization or storage device. (2) Adding indexes to speed up access — neither should require changing the logical schema.

🧠 Active recall

Which type is harder to achieve?
Logical data independence.
Why does a growing database need data independence?
Frequent changes at any level should not force redesign and re-implementation of the whole database.

6. DBA — Roles & Responsibilities 🟠 HIGH 2M ×× · 5M list

Intuition: The DBA is the "chief warden" of the database — decides who enters, keeps the building running, plans for disasters, and tunes performance. The overall goal: keep the server up at all times and give users the information they need, when they need it.

📌 DefinitionA Database Administrator (DBA) is the person/team responsible for managing the organization's information: authorizing access, coordinating and monitoring use, acquiring resources, and keeping the database protected with minimal chance of data loss. The DBA has a system/superuser account in the DBMS.

DBA responsibilities (PDF — core 7 from L1.1)

  1. Design of conceptual & physical schemas — interacts with users, writes schema definitions, stored permanently in the Data Dictionary.
  2. Security & authorization — grants different authorization types so no unauthorized access occurs.
  3. Storage structure & access-method definition — writes definitions translated by the DDL compiler.
  4. Data availability & recovery from failures — restores data to a consistent state after failure.
  5. Database tuning — modifies the database to ensure adequate performance as requirements change.
  6. Integrity constraint specification — constraints kept in a special system structure consulted on every update.
  7. Account creation — creates account id/password for users who need access.

Extended responsibilities (PDF L1.5 — SQL Server context)

Installing & upgrading the server · applying service packs · monitoring server health & tuning · managing storage · backup & recovery (most critical) · managing users & security · working with developers (normalization, indexes, triggers, stored procedures) · establishing naming standards · transferring data (import/export, DTS) · replication · data warehousing · scheduling events · providing 24-hour access · learning constantly.

🧠 Memory aid — core 7"3-S-D-A-T-I-A" → Schema design, Security, Storage structures, Data availability/recovery, Tuning, Integrity constraints, Account creation. Say it as: "Schemas, Security, Storage — then Availability, Tuning, Integrity, Accounts."
✍️ 5-mark structure — "Explain the role of DBA"1) Definition + overall goal — 1 · 2) Any 5 responsibilities with one line each — 3.5 · 3) Mention superuser account / data dictionary — 0.5.
🎯 Examiner focus"Backup and recovery is the DBA's most critical task" is a favourite one-liner. Mentioning the Data Dictionary and DDL compiler shows depth and earns marks.

Who is a DBA?
The person/team responsible for managing the organization's database: authorizing access, coordinating and monitoring use, ensuring security, backup/recovery and tuning. Holds the system (superuser) account.

(1) Schema design, (2) security & authorization, (3) backup & recovery, (4) database tuning. (Also: storage structure definition, integrity constraints, account creation.)

7. Schema vs Instance 🔴 MUST KNOW 2M ××× · 5M difference

Intuition: A class template in programming (declared fields, no values) vs the objects created from it (actual values at a moment). Schema = template; instance = the live data snapshot.

📌 DefinitionsDatabase schema: the skeleton structure / design of the database — the logical view defining how data is organized and how relations are associated, including all constraints. It contains no data and rarely changes.
Database instance: the data stored in the database at a particular moment of time — a snapshot that changes constantly as data is added/removed.

Three types of schema (PDF)

  • Physical schema — design at physical level: how data is stored in blocks of storage (files, indices).
  • Logical schema — design at logical level: tables, views, integrity constraints; programmers & DBAs work here; internal implementation hidden.
  • View schema (subschema) — design at view level: end-user interaction with the database.

✍️ 5-mark structure — "Differentiate schema and instance"1) Both definitions — 2 · 2) Comparison table (4–5 rows) — 2 · 3) The 100→200 records example — 1.

Likely 2-mark questions

Define database schema. Name its types.
The design/skeleton of a database defining how data is organized and related, with all constraints; it contains no data. Types: physical schema, logical schema, view schema.
What is a database instance?
The data stored in the database at a particular moment of time — a snapshot that changes whenever data is inserted, deleted or updated.
State two differences between schema and instance.
(1) Schema is the design and contains no data; an instance is the actual data at a moment. (2) Schema changes rarely; an instance changes constantly.

🧠 Active recall

Which is designed before the database exists — schema or instance?
Schema (designed when the database doesn't exist at all).
Programmers and DBAs work at which schema?
Logical schema.

8. Keys in DBMS 🔴 MUST KNOW 2M ×××× · 5M + problems

Intuition: In a classroom, "the tall boy" identifies nobody uniquely, but "roll no. 17" identifies exactly one student. A key is the attribute(s) that plays the roll-number role for a table — and also stitches tables together.

📌 Definitions — learn all six Super key: a set of one or more attributes that can uniquely identify a row in a table.
Candidate key: a super key with no redundant attribute — a minimal super key.
Primary key: the candidate key chosen (by DBA/designer) to uniquely identify rows; unique + not null; only one per table; underlined in diagrams.
Alternate (secondary) key: candidate keys not chosen as primary key.
Composite key: any key made of more than one attribute.
Foreign key: column(s) of a table that point to the primary/candidate key of another table — a cross-reference between tables.
Fig 8.1 — All candidate keys are super keys; one candidate becomes primary; the rest are alternate.
🖊 How to draw: Step 1 → big box "Super keys". Step 2 → smaller box inside "Candidate keys". Step 3 → two boxes inside that: "Primary" and "Alternate". Step 4 → side notes for composite (2+ attributes) and foreign (references another table's PK).

Foreign key example (PDF)

Course_enrollment(Stu_Id, Course_Id) — Stu_Id is a foreign key pointing to Student(Stu_Id). A foreign key value must either be NULL or exist in the referenced table. (PDF note: strictly, a FK can point to any candidate key, not only the primary key.)

Composite key example (PDF)

Sales(cust_Id, order_Id, product_code, product_count) — no single column is unique (a customer places many orders; an order has many products). Key = {cust_id, product_code} → a composite key.

Likely 2-mark questions

Define candidate key.
A super key with no redundant attribute — i.e., a minimal super key. Selected from the set of super keys; a primary key is chosen from candidate keys.
Differentiate primary key and foreign key.
Primary key: uniquely identifies rows of its own table; unique + not null; one per table. Foreign key: column(s) referencing the primary/candidate key of another table; may repeat and may be null.
What is an alternate key?
Candidate keys that were not selected as the primary key are called alternate (secondary) keys. Example: if Emp_Id is primary, Emp_Number is the alternate key.
What is a composite key? Give an example.
A key consisting of more than one attribute to uniquely identify rows. Example: {cust_id, product_code} in a Sales table where no single column is unique.
Super key vs candidate key.
A super key is any attribute set that uniquely identifies a row (may contain extra attributes). A candidate key is a super key with no redundant attribute (minimal). All candidate keys are super keys, not vice versa.

10. Relational Model 🔴 MUST KNOW 2M ×××× · 5M

Intuition: An Excel sheet with strict rules — every column one kind of value, no duplicate rows, single value per cell — is basically a "relation". The relational model (proposed by E.F. Codd) stores all data in such tables.

📌 Core terminology (favourite 2-markers) Relation: a table — data arranged in rows and columns. Tuple: a row (one record). Attribute: a column/field. Degree: number of attributes. Attribute domain: pre-defined set of allowed values for an attribute. NULL: value unknown/unavailable.

Properties of a relation (PDF)

  • All items in a column are of the same kind (same domain).
  • Each cell holds an atomic (single) value.
  • All rows are distinct (no duplicates).
  • Order of rows and order of columns is immaterial.
  • Each column has a distinct name.

Constraints in the relational model (quick map to T9)

Domain (AGE>0; value inside domain range) · Key integrity (key unique + not null, e.g., ROLL_NO) · Referential integrity (STUDENT.BRANCH_CODE must exist in BRANCH.BRANCH_CODE — STUDENT is the referencing relation, BRANCH the referenced relation).

Operations (PDF): Insert · Update · Delete · Select

  • Select — choose a specific range of data.

11. Hierarchical Model 🟠 HIGH 2M ×× · 5M compare

Intuition: A family tree or a company org-chart: every person has exactly one boss (parent), but a boss can have many subordinates (children). That's the hierarchical model — data as a tree.

📌 DefinitionThe hierarchical model (oldest model, developed by IBM in the 1950s) organizes data as a collection of segments in a tree-like structure where each record has one parent and many children (1:1 and 1:N relationships only). A segment with no parent is the root; segments with no children are leaves. Example system: IBM IMS (also NOMAD).
Fig 11.1 — Tree structure: one parent, many children; parent→child = 1:N.
🖊 How to draw: Step 1 → root box at top. Step 2 → children boxes below connected by lines. Step 3 → grandchildren (leaves) at bottom. Step 4 → label "1:N" on each parent→child link.

Features (PDF)

  • One-to-many relationships only; only one path from parent to any node.
  • Parent-child: each child has exactly one parent; multiple parents not allowed.
  • Deletion problem: deleting a parent auto-deletes all children under it.
  • Pointers link parent to child and are used to navigate.
💡 Advantages① Simple, logically clear structure; fast tree traversal. ② Data sharing (common database). ③ Data security (first model to offer it). ④ Data integrity via parent-child links; changes in parent reflect in child.
⚠️ Disadvantages① Complex to implement though conceptually simple. ② Lacks flexibility — deleting a segment cascades to all below it. ③ No standards. ④ Can't represent M:N relationships (child with two parents impossible). ⑤ Complex relationships unsupported.

Applications (PDF): semantic models for naturally hierarchical real-world structures (biological, political, social); physical models matching disk storage hierarchy (tracks, cylinders).

12. Network Model 🟠 HIGH 2M ×× · 5M compare

Intuition: Upgrade the family tree so a child can have two parents — now it's no longer a tree but a graph. A student linked to both the CSE department and the Library is the classic picture.

📌 DefinitionThe network model (formalized in the 1960s by the Database Task Group — DBTG) is a generalization of the hierarchical model that represents data as a graph of nodes (records) and edges (relationships), allowing a record to have more than one parent — thus supporting 1:1, 1:M and M:N relationships. A relationship is called a set, containing an owner record (≈ parent) and member record(s) (≈ child).

Features (PDF)

  • Graph structure — many-to-many relationships; multiple paths to the same record → faster access.
  • Records organized into records and sets; owner–member pairs; a member cannot exist without an owner → data integrity.
  • Navigational access via predefined paths (no declarative SQL); operations use a circular linked list.
  • Represents both hierarchical and non-hierarchical structures. Examples: TOTAL (Cincom), EDMS (Xerox).
💡 Advantages① Simple to design like hierarchical. ② Handles 1:1, 1:M, M:N. ③ Easy/fast data access via multiple paths. ④ Data integrity (member needs an owner). ⑤ Multi-parent relationships possible.
⚠️ Disadvantages / limitations① Very complex structure — records maintained by pointers. ② Operational anomalies; complex implementation. ③ Not user-friendly; needs advanced programming skill. ④ No automatic query optimization. ⑤ Lacks structural independence; least data independence. ⑥ Structural rigidity; performance overhead in navigation.

Operations (PDF): Insertion (add record + establish owner-member links), Deletion (remove record + maintain integrity), Update, Traversal (navigate predefined paths), Search.

15. Tuple Relational Calculus (TRC) 🟠 HIGH 2M ×× · 5M problem

Intuition: Relational algebra says "do step 1, then step 2". TRC just describes the answer you want — "give me all tuples t where condition P(t) is true" — and lets the system figure out how.

📌 DefinitionTuple Relational Calculus is a non-procedural query language where a query is expressed as { t | P(t) } — the set of all tuples t for which predicate P(t) is true. It specifies WHAT is wanted, not how to compute it. Notation: t[A] = value of tuple t on attribute A; t ∈ r = tuple t is in relation r. Quantifiers: ∃ (there exists), ∀ (for all). Connectives: ∧ (and), ∨ (or), ¬ (not).

17. Mapping Cardinalities 🟠 HIGH 2M ××× · 5M

Intuition: "How many of THESE can connect to how many of THOSE?" One person–one passport (1:1); one mother–many children (1:M); many students–one college (M:1); many students–many courses (M:N).

📌 DefinitionA mapping constraint (cardinality) is a data constraint that expresses the number of entities to which another entity can be related via a relationship set. For a binary relationship set R on entity sets A and B there are four mapping cardinalities: 1:1, 1:M, M:1, M:N.

18. Generalization, Specialization & Inheritance 🟡 MEDIUM 2M ×× · 5M possible

Intuition: Bottom-up: pigeon + sparrow + crow → "Bird" (generalization). Top-down: "Person" → student, teacher, staff (specialization). Children automatically get the parent's properties (inheritance).

📌 DefinitionsGeneralization: a bottom-up process in which a number of entities are combined into one higher-level generalized entity based on their similar characteristics (e.g., pigeon, house sparrow, crow, dove → Birds).
Specialization: the opposite, top-down process in which a group of entities is divided into sub-groups based on their distinguishing characteristics (e.g., Person → employee, employer, customer, vendor; or → teacher, student, staff).
Inheritance: the feature allowing lower-level entities to inherit the attributes of higher-level entities (Student and Teacher inherit name, age, gender from Person).

19. Domain Relational Calculus (DRC) 🟠 HIGH 2M ×× · 5M problem

Intuition: TRC picks whole rows ("give me tuples t…"). DRC picks column values directly ("give me values x1, x2… from the domains"). Same power, different variable type.

📌 DefinitionDomain Relational Calculus is a non-procedural query language (equivalent in power to TRC) in which variables take values from domains of attributes instead of tuples. General form: { <x1, x2, …, xn> | P(x1, x2, …, xn) } where x1…xn are domain variables and P is a formula built from comparison operators, connectives (∧ ∨ ¬) and quantifiers (∃ ∀). Queries must be safe expressions.

Solved queries (PDF) — loan(loan-number, branch-name, amount), borrower(customer-name, loan-number)

QuestionDRC expressionResult
Loan number, branch, amount of loans ≥ 100{ <l, b, a> | <l, b, a> ∈ loan ∧ a ≥ 100 }L01/Main/200, L03/Main/150
Only loan numbers of loans ≥ 150{ <l> | ∃ b, a ( <l, b, a> ∈ loan ∧ a ≥ 150 ) }L01, L03
Customer names + amounts for loans at "Main" branch{ <c, a> | ∃ l ( <c, l> ∈ borrower ∧ ∃ b ( <l, b, a> ∈ loan ∧ b = "Main" ) ) }Ritu/200, Debomit/60, Soumya/150
✍️ How to build any DRC answer (method)Step 1 → List the output columns as domain variables: { <c, a> | … }. Step 2 → For each table needed, write a membership atom <…> ∈ relation using shared variables for join columns. Step 3 → Add filter conditions (∧ b = "Main"). Step 4 → Wrap non-output variables in ∃.
🎯 Examiner focusThe difference sentence is the money line: "TRC uses tuple variables ranging over tuples; DRC uses domain variables ranging over attribute domains." DRC is the basis of the QBE (Query-By-Example) language style — worth one extra line if you know it, but the PDF only states equivalence with TRC.
⚠️ Source ambiguityThe PDF's teacher example says "department 8" in text but writes DEPT_ID = 10 in the expression — an internal inconsistency. Exam-safe: use the condition given in the question you receive; the structure matters, not the number.

Likely 2-mark questions

What is domain relational calculus?
A non-procedural query language where variables range over attribute domains (not tuples). A query has the form { <x1,…,xn> | P(x1,…,xn) } — values satisfying the predicate formula P. Equivalent in power to tuple relational calculus.
Write DRC for: loan numbers of loans with amount ≥ 150.
{ <l> | ∃ b, a ( <l, b, a> ∈ loan ∧ a ≥ 150 ) } — loan numbers for which there exists a loan tuple with amount at least 150.
State one difference between TRC and DRC.
TRC variables range over tuples of a relation ({ t | P(t) }); DRC variables range over domains of attributes ({ <x1,…,xn> | P }), selecting attribute values rather than whole tuples.

Problem type 1 — Find super keys, candidate keys, primary key

✍️ Step-by-step methodStep 1 → Identify attributes that are unique (ids, numbers) vs non-unique (names, ages). Step 2 → Every set containing at least one unique attribute is a super key. Step 3 → From super keys, drop any set from which you can remove an attribute and still keep uniqueness → survivors are candidate keys. Step 4 → DBA picks one candidate as primary; the rest are alternate.
💡 Solved (PDF)Employee(Emp_Id, Emp_Number, Emp_Name) — unique: Emp_Id, Emp_Number. Super keys: {Emp_Id}, {Emp_Number}, {Emp_Id,Emp_Number}, {Emp_Id,Emp_Name}, {Emp_Number,Emp_Name}, {Emp_Id,Emp_Number,Emp_Name}. Candidate keys: {Emp_Id}, {Emp_Number}. Primary: either one; the other becomes alternate.
⚡ Exam shortcutCandidate keys are usually the single unique attributes (or minimal combos when no single attribute is unique, like {cust_id, product_code}). Count super keys by combining unique attributes with any others.
⚠️ TrapA set with a unique attribute + a non-unique attribute is a super key but never a candidate key.
Practice: Student(RollNo unique, Email unique, Name, Age) — list candidate keys.
{RollNo} and {Email}. (Super keys: those two plus {RollNo,Email}, {RollNo,Name}, {Email,Name}, {RollNo,Age}, {Email,Age}, {RollNo,Email,Name}, … any superset.)

Problem type 2 — Write relational algebra queries

✍️ MethodStep 1 → Rows with a condition? Use σcondition(Table). Step 2 → Only some columns? Wrap with ∏cols(…). Step 3 → Two tables same shape, "or"? ∪. "but not"? −. Step 4 → Combine unrelated tables? × then σ to filter.
💡 Solved (PDF)Books published after 2010 or database books priced 450: σsubject="database" ∧ price="450" ∨ year>"2010"(Books). Authors of books or articles: ∏author(Books) ∪ ∏author(Articles).
Practice: find subjects of all books priced above 500.
∏subject(σprice>500(Books)) — σ first (rows), then ∏ (columns).

Problem type 3 — Write TRC / DRC queries

✍️ MethodTRC: { t | t ∈ R ∧ condition }; add ∃ s ∈ S ( t[x] = s[x] ∧ … ) per extra table. DRC: { <outputs> | <…> ∈ R ∧ condition }; share variables across atoms to join; ∃ the non-output variables.
💡 Solved (PDF)TRC — customers with loan AND account: { t | ∃ s ∈ borrower(t[c]=s[c]) ∧ ∃ u ∈ depositor(t[c]=u[c]) } → Saurabh, Mehak. DRC — customers+amounts at "Main": { <c,a> | ∃ l(<c,l> ∈ borrower ∧ ∃ b(<l,b,a> ∈ loan ∧ b="Main")) }.
⚠️ TrapForgetting the linking equality (t[x]=s[x]) — without it the tables are not joined and the answer is wrong.
Practice (TRC): find loan tuples with amount ≥ 5000.
{ t | t ∈ loan ∧ t[amount] ≥ 5000 }.
Practice (DRC): find branch names of loans above 1000.
{ <b> | ∃ l, a ( <l, b, a> ∈ loan ∧ a > 1000 ) }.

Problem type 4 — Referential integrity: allowed or rejected?

✍️ MethodStep 1 → Find the FK and the referenced PK. Step 2 → INSERT into referencing table: allowed only if FK value is NULL or exists in referenced table. Step 3 → DELETE/UPDATE in referenced table: blocked if the value is in use — unless ON DELETE/UPDATE CASCADE, which propagates the change.
